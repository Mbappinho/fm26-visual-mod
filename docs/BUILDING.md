# Building and testing

## Python installer and tests

Python, standard library only: tested with 3.14; 3.11+ expected. From the repository root:

```bat
python -B -m unittest discover -s tests
```

All tests use synthetic data. A few tests exercise real local inputs (your FIFA 17 install, a downloaded BepInEx zip,
a reviewed plugin build) and skip themselves when those inputs are absent.

## Plugin (`FM26.VisualDiagnostics.dll`)

Requirements: the **.NET 8 SDK** (it builds both the `net6.0` plugin and the `net8.0` policy tests), and the **IL2CPP interop assemblies generated by BepInEx from your own FM26
install**. Interop assemblies and BepInEx binaries are derived from / part of third-party software and are **never
committed** to this repository (`tools/leak_scan.py` fails on any `.dll`).

1. Install BepInEx be.788 into FM26 once (`python -m tools.fm26vm setup ...` or `python tools/deploy.py install`)
   and start FM26 once so BepInEx generates `BepInEx/interop/` in the game folder. Close FM26.
2. Build, pointing the project at the BepInEx core folder and at the generated interop folder:

```bat
dotnet build FM26.VisualDiagnostics.csproj -c Release ^
    -p:LoaderDir="<FM26 folder>\BepInEx\core" ^
    -p:InteropDir="<FM26 folder>\BepInEx\interop"
```

Without `-p:` overrides the project uses `.tools/bepinex-stage/BepInEx/core` (an unpacked BepInEx zip, git-ignored)
and `$(FM26Dir)/BepInEx/interop`, where `FM26Dir` defaults to the standard Steam location
`C:\Program Files (x86)\Steam\steamapps\common\Football Manager 26` (override with `-p:FM26Dir=...`).

The build cannot run in an environment without the interop assemblies (for example CI on a clean machine); this
is expected.

`tools/fm26vm/release.json` pins the SHA-256 of the release DLL. The project builds deterministically
(`Deterministic`, `ContinuousIntegrationBuild`, `PathMap`, `DebugType=none`, no source-revision suffix): no PDB path,
timestamp or checkout directory ends up in the DLL, so the same sources built with the same .NET SDK (the release was
built with 8.0.425) and the same reference assemblies give a byte-identical file, whatever the folder. If your hash
still differs (other SDK, other BepInEx/interop assemblies), `setup --plugin` refuses the file on purpose; use the
release asset, or update the pin in your own fork after reviewing your build.

## C# policy tests

`tests/PolicyTests` compiles the game-independent policy sources of `src/` against plain .NET 8 (no interop):

```bat
dotnet run --project tests/PolicyTests/PolicyTests.csproj
```

The suite needs only the .NET 8 SDK and the files of this repository; it exits with code 0 when every check passes.
It reads a few published fixtures: `tests/fixtures/fifa-overlay-live-001..004.*.json` (numbers extracted from the
plugin's own diagnostic reports: renderer flags/IDs, positions, timer ticks; no game asset) and
`tests/fixtures/baseline-0.2.12/SemanticEventObserver.cs` (this project's own 0.2.12 source, used as a regression
reference). Maintainer-only host checks (`tests/HostSegments`) are not published.

## Verifying a build against the release

If a Release build from this tree does not match the published asset byte-for-byte (different SDK or reference
assemblies), its decompilation should still be identical. To check, decompile both with ILSpy (`ilspycmd -p -o <dir> <dll> -r <LoaderDir>
-r <InteropDir>`) and compare the generated `.cs` / `.csproj` files.
